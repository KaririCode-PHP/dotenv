# ADR-005: OPcache-Friendly PHP Array Cache

## Status

Accepted — introduced in 4.2.0.

## Date

2026-02-28 · revised 2026-09-29 (4.5.0)

## Context

In production, `.env` files are static — they change only during deployments. Parsing the same file on every request wastes CPU cycles. The ideal cache format should:

1. Eliminate file I/O and string parsing entirely after first load.
2. Leverage existing PHP infrastructure (no external cache servers).
3. Be atomic — no partial reads during deployment.
4. Self-invalidate when source files change.

## Decision

### Format 2: a `var_export()` PHP array

The cache is a PHP file returning one array with a `meta` block and the `variables` block. Output of `bootEnv()` + `dumpCache()` (paths shortened):

```php
<?php

// Auto-generated by KaririCode\Dotenv — do not edit manually.
// Regenerate with: vendor/bin/kariricode-dotenv cache:dump

return array (
  'meta' =>
  array (
    'format' => 2,
    'generator' => 'KaririCode\\Dotenv',
    'generated_at' => '2026-09-29T11:21:06+00:00',
    'strategy' => 'bootEnv',
    'environment' => 'production',
    'requested_environment' => NULL,
    'encrypted' => false,
    'sources' =>
    array (
      0 => '/app/.env',
      1 => '/app/.env.local',
      2 => '/app/.env.production',
      3 => '/app/.env.production.local',
    ),
    'source_hash' => '226d86d394c062e9e3fdb5998bae4a1ac1daf19c642817847ed43930f4771fa7',
  ),
  'variables' =>
  array (
    'APP_ENV' => 'production',
    'DB_HOST' => 'prod-db',
  ),
);
```

Keeping variables under their own key means no variable name can collide with metadata. With OPcache enabled, the file is compiled once into shared memory and `include` returns the array without lexing or parsing.

### What the cache records and when it is reused

`sources` lists **every file the loader considered**, present or absent — for `bootEnv()` the whole cascade, including `.env.local` files that did not exist yet. `source_hash` is SHA-256 over each path with `mtime:size:inode`, or `absent`; `clearstatcache()` runs first so edits made earlier in the same process are seen. No file content is read.

`Dotenv` reuses a cache only when all of these hold; otherwise it parses the files, so a mismatch costs time but never serves wrong values:

| Check | Why |
|---|---|
| `format` is 2 and every field has the expected type | Files from 4.4 (format 1) or edited by hand are ignored. |
| `source_hash` matches the files now | Any edit, creation or deletion in the cascade invalidates it. |
| Same `strategy` (`load` or `bootEnv`) | A cache of `.env` alone must not stand in for the cascade. |
| Same `requested_environment` | The environment known before reading files — argument, `environmentName`, or process `APP_ENV`. A cache built for `staging` is not used when the process says `production`. |
| Same files (`load`: identical list; `bootEnv`: same base `.env` path) | A cache from another directory or file list is not reused. |
| If `encrypted`, a key is available | Otherwise the values could not be decrypted. |

### No plaintext at rest

When an encryption key is configured, `dumpCache()` stores **every** value encrypted (fresh nonce each), not only the ones that were encrypted in the source. This also covers plaintext derived from secrets, such as `DATABASE_URL="…${DB_PASSWORD}…"`. Values are decrypted on load by the normal pipeline.

### Atomic writes

The payload is written to `<path>.tmp.<random hex>` and moved into place with `rename()` (atomic on one filesystem); on failure the temporary file is removed and a `CacheException` is thrown. `opcache_invalidate()` is then called for the target path.

### Values stay strings

The cache holds raw strings. Type detection, casting and processors run on every load, so detectors, casters and processors registered at runtime apply identically to cached and parsed values.

### Load flow

```
load() / bootEnv()
  └─ cachePath configured? ── no ──► parse files
        │ yes
        ▼
  PhpFileCache::load(): format + field types + source_hash ── fail ──► parse files
        │ ok
        ▼
  same strategy, requested environment, files, key available? ── no ──► parse files
        │ yes
        ▼
  setVariable() for each value (decrypt → cast → processors), source = "cache"
```

## Consequences

### Positive

- No parsing when the cache matches; OPcache serves the array from shared memory.
- Editing, adding or removing any cascade file invalidates the cache automatically.
- The cache never holds plaintext when a key is configured.
- Every mismatch falls back to parsing — the cache can make loading faster, never different.

### Negative

- An encrypted cache costs one AES-GCM decryption per variable per load (microseconds each).
- Detection uses metadata: an in-place edit that keeps the same size within the same second and the same inode is not noticed. Deploy tools that replace files change the inode.
- Paths are absolute, so dump the cache on the target host, in the deploy step.
- With `opcache.validate_timestamps=0`, running `cache:dump` from the CLI does not reach PHP-FPM's shared memory: reload PHP-FPM (or reset its OPcache) after dumping.
- Caches written by 4.4 are ignored after upgrading until they are dumped again.

## Alternatives Considered

| Alternative | Why not |
|---|---|
| APCu | requires ext-apcu and is per-SAPI. |
| JSON file | `json_decode()` on every request is slower than an OPcache-backed `include`. |
| `serialize()` | slower than `include` for arrays and unsafe with untrusted input. |
| Hashing file contents | exact, but reads every file on each request, which the cache exists to avoid. |
| Hashing only the constructor's file list (4.4 behavior) | missed edits to `.env.local` and `.env.{env}` under `bootEnv()`. |
